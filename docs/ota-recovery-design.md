# OTA 掉电恢复：可行性分析与方案选型

> 状态：**选型待定**。本文给出现状实测、物理约束、候选方案与推荐意见。
> 基线：2026-09-17 构建实测（Flash 39,616 B / RAM 19,896 B）。
> 结论先行：**64KB 单 Bank 上做不了完整 A/B**，必须在「缩减固件」和「换恢复机制」之间选一条。

---

## 一、硬约束（实测，不是估算）

| 项 | 实测值 | 说明 |
| --- | --- | --- |
| STM32F103C8T6 Flash | 65,536 B | 单 Bank |
| Bootloader | 7,040 B | 8KB 分区，占 86% |
| Config 区 | 2,048 B | 当前只用 1 页（1,024 B），单副本 |
| **Application 镜像（firmware.bin）** | **39,008 B → 本次改动后约 39,616 B** | OTA 实际传输的就是这个大小 |
| Application RAM | 19,896 B / 20,480 B | **97.1%，只剩 584 B** |
| Flash 占用率 | 60.4% | |

### A/B 是否可行

```
可用给 Application 的空间 = 65536 - 8192(boolloader) - 2048(config) = 55,296 B
双槽每槽            = 55296 / 2 = 27,648 B = 27 KB
当前镜像            = 39,616 B = 38.7 KB
缺口                = 39,616 - 27,648 = 11,968 B ≈ 11.7 KB
```

**结论：A/B 在物理上不成立。** 缺口 11.7 KB。

有没有可能靠瘦身补上？看 Flash 构成（`arm-none-eabi-size -A` 实测）：

| 段 | 大小 | 内容 |
| --- | --- | --- |
| `.text` | 31,432 B | HAL 驱动（SPI/I2C/UART/RCC/FLASH）+ FreeRTOS + 全部 UI/传感器代码 |
| `.rodata` | 7,192 B | `g_chinese_glyphs` 2,074 B、`OLED_F8x16` ×2 共 3,040 B、`crc32_table` 1,024 B、字符串常量 |
| `.isr_vector` | 268 B | 向量表 |
| `.ramfunc` | 72 B | RAM 中执行的 Flash 写函数 |

即使**全部删掉** UI 层 + 两个字库 + 中文字形（≈ 9 KB）也只能省到 30 KB，仍大于 27 KB，而且会毁掉项目最有说服力的本地终端能力。**瘦身不可行。**

## 二、当前方案的失效模式（代码实测）

`bootloader/Core/Src/main.c` 的 `process_ota_chunk()`：

```
addr = APP_BASE + (seq * FLASH_PAGE_SIZE)
flash_erase_page(addr);          // ← 收到第 seq 个 chunk 就擦掉那一页
flash_program_halfword(...);
```

因此：

| 失效时刻 | 后果 |
| --- | --- |
| 收到 seq=0 后、OTA 未完成时掉电 | page0（含向量表）已被擦除 → `app_is_valid()` 返回 false → 停在 maintenance，**必须重新 OTA 或 ST-Link 重刷** |
| 收到 seq≥1 后掉电 | page0 可能完整，但 page1..N 已是新固件内容 → 旧固件代码被破坏，启动即 HardFault 或跑飞 → 看门狗复位 → 循环 |

> **重要纠正**：一个看似合理但错误的想法是"把 page0 放到最后写就能防砖"。这不成立——旧固件 99% 的代码位于 page1 之后，第一个 chunk 写入 page1 时旧固件就已经不可能再运行了。page0 完整只影响 `app_is_valid()` 的返回值，不影响实际可运行性。

**所以：不做真正的镜像冗余，就无法在"传输中途掉电"后自动回到旧固件。** 能做到的是——**不把它变成砖**，而是变成"可被主机自动修复的状态"。

## 三、候选方案

### 方案 1 · 缩减固件换取真 A/B

把镜像压到 ≤ 26 KB，双槽各 26 KB。

| 优点 | 缺点 |
| --- | --- |
| 真正原子切换 + 可回滚，最接近生产级 | 需砍掉 UI/字库/部分 HAL，约 -13 KB |
| 面试叙事最强（"我在 64KB 上实现了双槽"） | 会毁掉本地终端这个已经很值钱的能力 |
| 与 MCUboot 的 direct-xip 模型同构 | 工作量大，需改链接脚本、bootloader、ESP32 校验、PC 工具 |

**判定：不推荐。** 用项目最有说服力的功能去换一个"听起来高级"的机制，性价比为负。

### 方案 2 · 跨设备冗余 + 启动确认（推荐）

核心洞察：**另一份"已知良好固件"已经在 ESP32 上了。**

STM32 拿不出第二份镜像的空间，但 ESP32 有 4 MB Flash 和 SPIFFS。把恢复责任跨设备分配：

```
发送新固件前：ESP32 保留上一版已确认可用的镜像（golden）
升级成功后：  新固件自证健康 → 通知 ESP32 更新 golden
升级失败后：  bootloader 识别"上一次升级没被确认" → 停在恢复窗口等待
               ESP32 探测到恢复状态 → 自动重推 golden → 设备恢复
```

需要的最小实现：

| 组件 | 改动 | 成本 |
| --- | --- | --- |
| Bootloader 启动确认计数 | 每次启动把尝试计数 +1（存备份寄存器 `BKP_DR`，不写 Flash，无擦写寿命问题）；应用启动 3 s 后写"已确认" | ~40 行 |
| 恢复窗口 | 计数 ≥ 3 时把 OTA 窗口从 200 ms 延长到 10 s 并慢闪 LED，明确广播"我需要恢复" | ~15 行 |
| Config 双副本 | 见下节 P0-2，让"待确认"状态本身掉电安全 | 中等 |
| ESP32 golden 镜像 | 保留上一版镜像 + 探测恢复状态 + 自动重推 | 中等 |
| 镜像完整性 | bootloader 用 `cfg.image_crc32` 复核 app 区，识别"传输了一半" | ~20 行 |

| 优点 | 缺点 |
| --- | --- |
| 不牺牲任何现有功能（RAM/Flash 几乎不涨） | 恢复依赖 ESP32 在线 |
| 多处理器协同 + 看门狗下的看门狗，面试叙事比普通 A/B 更有辨识度 | 不是纯 MCU 单机方案，纯 MCU 岗面试官可能追问"没有 ESP32 怎么办" |
| BKP 寄存器方案完全不消耗 Flash 擦写寿命 | 需要证明 BKP 在复位/掉电下的行为（VDD 掉电会丢，要设计成"丢了也不致命"） |

**判定：推荐。** 它承认物理约束并给出真正能工作的恢复路径，而不是假装做到了 A/B。

### 方案 3 · 只做"不砖 + 可诊断"，接受手动恢复

| 改动 | 效果 |
| --- | --- |
| Config 双副本 + seq 轮换 | 升级意图本身掉电安全 |
| 启动失败计数 + 延长恢复窗口 | 设备不会无提示地停在 maintenance，而是明确广播 |
| 诊断状态可查询 | 能回答"上次升级为什么失败" |

不实现自动重推，恢复由人手动触发一次 OTA。

**判定：作为方案 2 的子集先落地。** 如果时间紧，先做这一层就已经比现状好得多，且不依赖 ESP32 侧工作。

## 四、配置区双副本的物理约束（影响设计）

当前 config 区 2 页（62、63），每页 1,024 B，`BootConfig_t` 48 B。

**看似直接的做法**：把两份 48 B 配置放在同一页的两个固定偏移，写入时切换偏移。

**为什么不行**：Flash 只能按页擦除。切回第一个偏移时必须擦整页 → 两份同时消失 → 擦除与写入之间掉电就全丢。**同页双副本在当前硬件上无法提供原子性。**

**可行做法**（三选一）：

| 做法 | 代价 | 原子性 |
| --- | --- | --- |
| A. 每份配置占一整页，ping-pong（需要 2 页） | 现在的 2 页刚好够，但**没有余量** | ✅ 真原子 |
| B. 从 Application 区挪 1 页给 config | Application 缩到 53 KB | ✅ 真原子 |
| C. 把配置写成追加日志（每页内顺序追加，写满才擦） | 实现复杂，需处理页内偏移与回绕 | ✅ 且擦写寿命更好 |

**推荐 A**：不改变现有分区契约，2 页刚好放两份。代价是 config 区没有任何剩余空间，但当前也没有别的用途。

> 注意：当前 `ota_config_write()` 的顺序是"擦页 → 写 → 回读校验"，本身就存在擦除后掉电即全丢的窗口。方案 A 让另一页始终持有上一份有效配置，把这个窗口消除。

## 五、推荐落地顺序

| 顺序 | 项 | 依赖 | 验收 |
| --- | --- | --- | --- |
| 1 | Config 双副本 ping-pong（第四节方案 A） | 无 | 写入过程中断电，重启后仍能读到上一份有效配置 |
| 2 | Bootloader 用 `cfg.image_crc32` 复核 app 区 | 1 | 人为写坏半张镜像 → 启动时被判为无效并进入恢复窗口 |
| 3 | 启动确认计数（BKP）+ 延长恢复窗口 | 1、2 | 连续 3 次启动失败后自动进入 10 s 恢复窗口并慢闪 |
| 4 | ESP32 保留 golden 镜像 + 探测恢复 + 自动重推 | 3 | 传输中途断电 → 上电后自动恢复到旧版本，无需人工干预 |
| 5 | 故障注入回归脚本（覆盖上述路径） | 全部 | 见 `docs/ota-regression-template.md` |

第 1–3 项是纯 STM32 侧，不依赖 ESP32 侧改动，可以立刻开工。第 4 项决定"能否自动恢复"，是方案 2 的核心价值。

## 六、需要拍板的决策点

1. **是否接受"恢复依赖 ESP32 "？** 接受 → 走方案 2；不接受且坚持纯 MCU 单机恢复 → 只能在方案 1（砍功能）和方案 3（手动恢复）之间选。
2. **Config 双副本采用 A / B / C 哪种？** 推荐 A（不改分区契约）。
3. 若走方案 2，是否同意在 ESP32 SPIFFS 里长期保留一份 golden 镜像（约占 40 KB，ESP32 有 4 MB，无压力）？
